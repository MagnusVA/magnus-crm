How it works

The API answers from two places. History comes from the reporting database, and today comes straight from the CRM.

History: /metrics and /funnel

Fivetran copies the CRM into the reporting database about every 6 hours. Each answer is cached, so asking the same question again costs a few hundred milliseconds. Every answer carries as_of: it includes every change up to that moment.

Today: /today

Today is read live from the CRM on every call, with the same metric definitions as history. Use it for the current day and /metrics for anything that ended before today.

What happens to a request

Quick start

Three steps from no key to a working dashboard feed.

Create a key

An owner or admin opens Settings › Integrations › API keys and creates one. The full key shows once, so store it in your server's secrets. Each workspace can have 10 active keys.

Call an endpoint

Send the key as a bearer token from your server. Never put it in a browser or a mobile app; anyone holding it can read the workspace's metrics.

Read data and meta

data holds the numbers. meta.as_of says how fresh they are. A 202 means the range is being computed; retry after Retry-After seconds.

Endpoints

All five are GET, return JSON, and need the bearer key.

Metric catalog

Sixteen metrics. Each counts on a specific day, and each supports the groupings marked below. Asking for a grouping a metric doesn't support returns 400.

Units. Counts are whole numbers. Money is in minor units (cents) with a currency on every row. Rates run from 0 to 1, and are null when there is nothing to divide by.

Freshness

When the reporting data was last refreshed, and when the next refresh is expected. Cheap to call; it never touches the reporting database.

Today, live

Read from the CRM on every call. meta.date is today in the workspace's business day, and meta.partial turns true only on a day busy enough that a reading stops early.

Funnel

Five totals in one call: captured, qualified, booked, held and won. Here October 1 to 27 (27 days) against September (30 days).

Not a cohort. Each step counts on its own day: a capture on its capture day, a call on its scheduled day, a win on the day its first payment arrived. The ratio between steps compares volumes in the same window; it doesn't follow the same people through.

Daily trends

granularity=day returns one row per metric per day. Two calls, 28 days each, ending yesterday.

Weekly attendance

granularity=week names each week by its Monday. Counts and rates come back in the same call; they're plotted apart because they don't share a scale.

Cash by month

granularity=month names each period YYYY-MM. Money rows come one per currency, and the API never converts between them.

Breakdowns

granularity=total with group_by turns a range into a leaderboard. group_id is an id; join it with dimensions for names. All four use October 1 to 27.

Errors and status codes

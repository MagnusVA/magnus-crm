MAGNUS CRM · RELEASE OPERATIONS

Booking and reporting migration checklist

Rehearse in dev before merging. In production, deploy the widened release, adopt receipts, rebuild from source, drain work, verify and activate each intended tenant.

Merging or deploying does not finish the data migration. Existing tenants stay blocked from V2 reports until the rebuild is verified and activated. The current overview can show "Section unavailable" during that interval.

This offline document never runs commands or calls the CRM. Copy buttons only copy text. No migrations, production deployment or data repair were performed to create it.

1. RehearseChecks and dev cutover before merge.
2. PrepareBackup, target, controlled writes.
3. DeployAligned backend, pools and frontend.
4. RebuildReceipts, projections, drain, assertions.
5. ActivateTenant readiness and source reconciliation.

CLI setup: Create a private environment file outside the repository for each target. Use that deployment's CONVEX_DEPLOY_KEY, or its exact CONVEX_DEPLOYMENT with an authorized CLI account. Verify which deployment the file selects in the Convex dashboard before any write. Never enter a key in this document. Commands use the installed CLI with --env-file, which overrides .env.local. This avoids local deploy keys overriding --prod or rejecting --deployment dev.

Checks record your review; they are not verified execution results. Dev and production checkmarks are kept separately when browser storage is available.

Merge only after the migration has been rehearsed and the release procedure is ready.

04 / CHECKPOINT
Adopt retained webhook deliveries
Adoption creates logical receipts and retains provider facts. It does not replay historical CRM business writes.
Inspect the six rollout migrationsread
Run after each migration. Require the relevant entry to have isDone: true, state: success and no error. An unknown entry has not run. A runner returning successfully does not prove completion.
Dry-run receipt adoptiondry-run
One batch only. The migrations library rolls back the batch through its DRY RUN mechanism. Read the result carefully; it does not prove complete-table coverage.
Start receipt adoptionwrite
Wait for adoptWebhookDeliveryReceipts to complete before starting its assertion.
Assert every retained raw row has a receiptwrite
This migration records verification progress. Wait for assertWebhookDeliveryReceipts to complete.
05 / CHECKPOINT
Rebuild reporting from source meetings
The rebuild enqueues a projection for each source meeting, in batches of 32. Workpool processing happens afterward.
Dry-run projection enqueuedry-run
One batch. Its transaction and queued jobs roll back. A dry run does not execute the reporting worker or validate the final buckets.
Start the source-meeting rebuildwrite
Wait for rebuildMeetingProjections to complete, then wait for reporting work to drain. These are two separate conditions.
Inspect tenant reporting and webhook workread
Checks up to 101 rows per queue. 100+ means capped, not exactly 100. Reporting queued and failed counts must be zero. Webhook blocked items require classification; they are not an automatic reporting-activation failure.
Stop here if jobs remain queued or failed.
The cron reports stale work; it does not rescue it. Investigate stuck jobs and completion callbacks. Do not set the activation flag to get past the banner.
06 / CHECKPOINT
Run fresh verification in order
Keep source records stable, inspect each result and finish one assertion before starting the next.
1. Verify source meetingswrite
Checks meeting/opportunity tenant relationship, expected bucket key, applied projection and bucket existence. Uses batches of 64.
2. Verify ledger sourceswrite
Checks applied projection state, tenant consistency, deleted-source contributions and contribution-key consistency. Uses batches of 64.
3. Verify exact bucket totalswrite
One bucket per batch. Each positive bucket must equal its indexed contribution count. A bucket with more than 8,192 contributions rejects verification; resolve that scale limit before activation.
Verification condition
The activation mutation checks completion flags, not an immutable proof tied to this rebuild. The operator must establish that these assertions belong to the current source state. If that cannot be established, hold activation.
07 / CHECKPOINT
Activate reporting for the intended tenant
Use the guarded internal activation mutation after reviewing the evidence. Do not patch the version field directly.
Activate verified V2 reportingwrite
Run once per reviewed tenant. It requires the rebuild and three assertions to be completed and no queued/failed reporting work for this tenant. It does not require the two receipt migrations; finish those separately above.
08 / CHECKPOINT
Close out the release and historical repairs
Deployment does not decide which historical records should be replayed or split.
09 / CHECKPOINT
If a checkpoint fails
Hold the next step, preserve data and correct the specific failure.
FailureResponse
Dry run, migration or assertion errorsSave the error and migration status. Repair the cause. Resume the failed migration without reset to continue from its cursor, or deliberately restart after review. Never run concurrent resets.
Reporting job failsThe committed source outcome remains. Repair the bucket/relationship or other cause, retry the current failed generation, drain and run fresh assertions.
Queued work never completesInspect Workpool and scheduled jobs/callbacks. The alerting cron has no automatic rescue. Keep reporting inactive until a reviewed recovery succeeds.
Frontend/backend release mismatchKeep the maintenance window and align the release versions before continuing.
Old-code rollback is requiredControl ingress/writes and preserve widened tables. Old writers stop maintaining V2. Do not leave V2 readers active with them. There is no dedicated deactivation helper in this release; establish the corrective release/reader plan before rolling back.
Data restore is proposedUse the isolated restore rehearsal and a reviewed reconciliation plan for writes after the backup. Never import a snapshot over live payments, events and tenant data as a reflex.
For a failed migration, rerun its migrations:run command with the same fn and omit reset. Completed verification must be explicitly restarted after input changes.
Release record and evidence
Record deployment identifiers, backup path, status outputs and timestamps, queue measurements, report reconciliation, approved repairs, observation thresholds and rollback owner. Keep credentials and customer payloads out of this document.

MAGNUS CRM Vercel usage audit · Oct 21 to Nov 4, 2026

Every five minutes, each open tab throws its cache away.

I went through 14 days of production metrics, sliced them down to single clients in 5-minute windows, and traced the cause through the Next.js and AuthKit source. Most of the usage comes from one loop. AuthKit refreshes the access token with a server action that writes a cookie. Next 16 treats that as a full revalidation, clears every prefetched route in the tab, re-renders the page on the server, and lets the sidebar prefetch everything again. Favicons, the PostHog proxy and a log webhook make up most of the rest.

The short version

Two Hobby limits broke, and one loop drives both

At the current pace the app makes about 1.78 million CDN requests and burns about 6.2 active CPU-hours a month. Hobby includes 1 million requests and 4 CPU-hours. Pro's flat-rate CDN tier also starts at 1 million requests, so this matters after the upgrade too.

The rendering setup isn't the problem. With cacheComponents and partialPrefetching on, 98% of workspace page requests come out of the CDN cache, and Convex moves all live data over its own WebSocket, which Vercel never sees. The problem is what keeps asking for those cached shells, and how much it costs to ask. Each prefetch is a cache hit, but the WorkOS proxy runs before the cache, and every proxy run costs at least 10 ms of CPU. Middleware burned 109 CPU-minutes in two weeks. All functions together burned 63.

Moving the token refresh into a Route Handler kills the loop. With that, the favicon fix and the log webhook fix, you'd land around 865,000 requests and 2.4 CPU-hours a month. Take PostHog off the proxy too and requests drop near 500,000.

The fixes, ranked by what they save

Eight changes, and the first one does most of the work

Savings are monthly at current traffic. Estimates say so. Savings overlap, so don't add them up blindly. The waterfall further down does the arithmetic in order.

01

Refresh the token through a Route Handler, not a server action

Add app/api/auth/token/route.ts, have fetchAccessToken call it, and drop useAccessToken() so AuthKit's own refresh timer and focus listeners never start. Pass onSessionExpired={false} to AuthKitProvider as well, so a tab switch stops costing a checkSessionAction POST. A cookie written by a Route Handler doesn't trigger Next's action revalidation. So the prefetch cache survives, and the server stops re-rendering the page every five minutes. Convex already schedules a refresh before expiry, and a failed refresh is your signal to show the session-expired toast.

app/api/auth/token/route.ts · newimport { getTokenClaims, refreshSession, TokenRefreshError, withAuth } from "@workos-inc/authkit-nextjs";

// A Route Handler, not a server action. A cookie written here doesn't make
// Next clear the client's prefetch cache or re-render the current page.
// The proxy already refreshes a token close to expiry and hands it over.
// tokenResponse(token, status = 200) answers JSON with Cache-Control: no-store.
export async function POST(request: Request) {
  const site = request.headers.get("sec-fetch-site");
  if (site && site !== "same-origin") return new Response(null, { status: 403 });
  const force = ((await request.json().catch(() => null)) ?? {}).force === true;

  const { user, accessToken } = await withAuth();
  const claims = accessToken ? await getTokenClaims(accessToken) : null;
  // Forced, but issued in the last 30 s: the proxy just refreshed it.
  if (user && accessToken && (!force || Date.now() / 1000 - (claims?.iat ?? 0) < 30)) {
    return tokenResponse(accessToken);
  }
  // Forced, or the proxy found no usable session. Refreshing tells
  // no cookie and a dead refresh token (401) from a WorkOS outage (503).
  try {
    const refreshed = await refreshSession();
    return refreshed.user ? tokenResponse(refreshed.accessToken) : tokenResponse(null, 401);
  } catch (error) {
    if (error instanceof TokenRefreshError && error.isTransient) return tokenResponse(null, 503);
    // Another tab spent this refresh token first; the current token still works.
    if (user && accessToken && (claims?.exp ?? 0) > Date.now() / 1000) return tokenResponse(accessToken);
    return tokenResponse(null, 401);
  }
}

Three things load on every route that most routes don't need. SSR, ISR and server actions

What each kind of page should do

You asked whether Convex being client-heavy means you're using Next wrong. Mostly no. Convex is the reason this app can be cheap on Vercel.

Every Convex query and mutation in the browser goes over a WebSocket straight to Convex, and Vercel never bills for it. So Next has a narrow job here. It serves a static shell from the CDN, checks auth once per document load, and gets out of the way. ISR and "use cache" are built for shared content that changes rarely. Tenant data in a CRM is neither, so keep them away from it. The one server action in the hot path that you didn't write, AuthKit's refresh, turned out to be the most expensive thing in the app. That's the lesson. On Next 16, any server action that writes a cookie clears the client cache.

Transitions

The page transition CSS is there, but nothing triggers it

app/globals.css:257-285 defines a page-transition cross-fade, and its comment says workspace-shell-client.tsx triggers it with <ViewTransition default="page-transition">. That component isn't in the file anymore, so the CSS never runs. React 19.3 ships <ViewTransition>, and the Next 16 guide says it works in the App Router with no config, because route navigations are already transitions.

Here's what I'd add, in order. First, wrap the page slot in the shell with <ViewTransition default="page-transition">, which brings back the cross-fade between workspace pages. Second, wrap the Suspense boundaries on lists so the skeleton fades into content instead of popping. Third, give the meeting row and the meeting detail header the same name so the row grows into the page when a closer opens a meeting. Your reduced-motion rule at globals.css:388 already turns all of it off for people who ask.

Fix 01 matters for speed too. Today a navigation that lands right after a refresh finds the prefetch cache empty and waits for the network. With the loop gone, the shell is already in memory when someone clicks.

Checked and withdrawn, or ruled out

What I got wrong, and what I ruled out

  • I withdrew raising staleTimes.static. It does set shell freshness, but expiry is checked lazily, and a link that stays visible never re-prefetches on its own. The metrics agree. No client ever had a prefetch burst without a POST.
  • I withdrew bot protection. 1,036 MB of the "unknown bot" traffic is the Convex log stream, user agent Convex/1.0. A challenge rule would have broken error tracking. The rest is a few crawlers on public pages.
  • I corrected the token refresh to one per 5 minutes, not two. AuthKit's token store deduplicates the in-flight refresh with Convex's request.
  • Rewriting proxy.ts for speed won't help. Middleware CPU sits at a 10 ms floor on every path.
  • The proxy fetched WorkOS signing keys 7,805 times in a week, because each new instance starts with an empty key cache. It's annoying but small, and it shrinks with fix 01.
  • Lead-gen capture, meeting detail and the home page looked like caching gaps. Every uncached request on them is a POST, and every GET already hits the CDN.
  • I didn't recommend Fluid compute, memory or region changes. Fluid is on, memory is the 2 GB default, and functions run in iad1 next to Convex.
  • ISR writes are zero across the app, so there's no revalidation to tune.
Method

Where these numbers come from

Usage totals are 14-day sums from Vercel Observability Plus for project magnus-crm, collected Nov 4, 2026, multiplied by 30/14 for monthly figures. The loop analysis used the is_prefetch_request, client_ip and request_method dimensions at 5-minute resolution, and upstream latency came from the external API metrics. I traced the cause through the installed source of next 16.4.3 and @workos-inc/authkit-nextjs 4.4.0.

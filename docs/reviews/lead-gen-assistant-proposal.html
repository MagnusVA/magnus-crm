Proposal. A design for the next toolsets on the Magnus MCP gateway. Every window below is simulated in this page. Nothing talks to Magnus, Claude, ChatGPT, Slack or Instagram. Every person, handle, post and number is invented. The client screens are approximations drawn to show the flow.

The lead gen assistant: 22 tools for lead gens and the admins who run them

The closer assistant gave phone closers an AI companion over MCP. This document designs the same thing for lead gens and for the admins who manage lead gen. It covers a lead gen's day, the actions they take, and the Operations report. Thirteen tools ship first with no schema change. Six more follow with new readers, and three wait on new tables.

Starting pointWhat the code says today

Seven investigators read the gateway, the lead gen pages, the report readers, the admin functions and the closer plan. This is what they found.

The piping is there

  • One /mcp endpoint with AuthKit sign-in. The gateway takes one flat catalog and filters every tool by metadata.roles, so a second and third toolset fit on the same URL.
  • tenants.mcpAccess.roles already accepts all four roles. The Settings card already shows disabled "No tools yet" rows for lead gens and admins.
  • Confirm tokens, the per-user rate limit of 60 calls a minute, the audit log and the per-member block all carry over.

Three lines keep it closer-only

  • MCP_TOOLSET_ROLES = ["closer"] in convex/mcp/guard.ts:22
  • "mcp:connect": ["closer"] in convex/lib/permissions.ts:55
  • closerInstructions is the only instruction set, and the Settings, Team and Profile cards say "closer" in their copy.

What a lead gen can't do today

  • Ask "have we captured this handle?" without capturing it. Submitting is the only lookup, and it counts a dupe.
  • Capture more than one handle at a time.
  • Undo a capture. Only an admin can void one.
  • See what happened to the people they captured.

The lead gen's three screens

  • Capture. Set an origin such as a reel, then paste profiles one at a time. The band shows Today, Unique and Dupes.
  • Respark. Claim a batch of 45 stalled people from the team pool, held until the business day ends at 1:00 AM. Mark each one Resparked, Not a fit or Skip.
  • My Activity. Raw leads, resparks, entries, not a fit and leads per scheduled hour.

The admin's report, Operations › Lead Gen

  • Totals, specialists by team, top posts by team, prospect conversion and respark performance.
  • Today reads Convex live. Longer ranges read ClickHouse, synced about every six hours, merged with today's live figures.
  • It shows no cash, no closed deals and no show rate. Schedules are hours per weekday. Nobody clocks in.

Act 1Sofia's day

1Start of shift

Sofia opens Claude and asks one question. The answer is the Capture band and the Respark start screen in one reply. The tool takes no arguments, because the sign-in already says who is asking.

What to notice
  • One call, counts only. No person's details load until Sofia asks for them.
  • An inactive profile comes back as profile: "inactive". The web returns zeros there, which an assistant would read as "you captured nothing".
  • Her follow-up about the pool needs no second call.
Decisions this raises
  • Whether the reply should include the origin she used last. Here it does, so the assistant can ask "same reel as Friday?"

2Before she messages anyone

Today, the only way to learn whether a handle is already in Magnus is to capture it. That counts a dupe and can't be undone. This tool is new. It looks handles up and writes nothing.

What to notice
  • The Capture band stays at zero. A check is not a capture.
  • Sofia learns that someone captured @coachdre_ before, and that it was a teammate. She does not learn which one.
  • "Do not contact" comes back before she writes to the person. Today it shows only after the capture is saved.
Decisions this raises
  • The check answers for any handle in the workspace. It is capped at ten handles a call, rate limited and audited. It returns the same stage and warning the capture confirmation already shows.
  • Whether a lead gen should see the teammate's name. The respark card on the web shows it today.

3Eight handles from one reel

Sofia pastes a reel and the handles she found in its comments. A lead gen can't undo a capture, so the tool previews the whole list first. One yes covers the list.

What to notice
  • Magnus writes the preview. The model reads it back word for word, and the token only works with the same list.
  • The do-not-contact handle is left out unless Sofia asks for it by name. The web would have saved and counted it.
  • The commit is one transaction. If any line fails, nothing saves.
  • The last beat repeats the commit after a dropped connection. Magnus returns the first result and writes nothing.
Decisions this raises
  • The cap starts at ten handles a commit. Each capture reads and updates the daily and origin counters, so the cap rises only after measuring a real transaction.
  • Each capture still posts to the lead gen Slack channel, as it does from the web. Six captures are six posts.

4Working a respark batch

The assistant claims the batch, briefs Sofia on a person and drafts an opener. Sofia sends it from her own Instagram. Then she tells the assistant what happened, and one read-back records five results.

What to notice
  • Magnus never sends a message. It has no way to, and the instructions say so.
  • Nina's booking answer contains a line written to look like an instruction. It arrives marked as her words. The assistant tells Sofia and ignores it.
  • Not a fit has a five-second undo on the web and none on the server. Here it sits behind the read-back.
  • Phone and email stay masked, and the card drops the "payment recorded" touch that the web card shows.
Decisions this raises
  • Twenty marks a commit means a batch of 45 takes three confirmations. One per person would take 45, and 90 calls against a burst limit of 20.
  • Skip writes nothing on the person, but it hides them from Sofia for the day. It goes through the same read-back.

5Wrapping up, and what it won't say

Sofia finishes from ChatGPT on her phone. Her numbers come from the same readers as My Activity. Then she asks for two things the assistant has no tool for.

What to notice
  • Today is live. The month is history as of the 6:10 AM sync, plus today. The result says which is which.
  • No tool in Sofia's list returns a teammate's numbers or a payment, so the assistant has nothing to leak.
  • She can't undo her own capture. The assistant hands her the exact line to give Jordan.
Decisions this raises
  • A lead gen end-of-shift report to Slack, like the closers have, needs its own builder and a table. It is in the "later" group.
  • Whether lead gens may see what happened to their own captures. That is magnus_my_lead_gen_outcomes in release 2.

Act 2Jordan's day

6The Monday review

Jordan asks for last week by person, by team and by post. One call returns four sections of the Operations page. The page sits beside the chat so you can check each figure.

What to notice
  • The tool calls the same builders and merge functions as the page, so the numbers match by construction. A parity test holds them together.
  • The result carries its own definitions. Teams roll up by each specialist's current team. Posts group by the team at capture time.
  • Jordan's question about cash gets a plain "Magnus doesn't have that here".
Decisions this raises
  • Whether the production tenant reads lead gen from the warehouse yet. If it doesn't, ranges over seven days go through the snapshot job and take longer.
  • Whether admins want bookings and cash per post. The data is stored. No reader exists.

7A live floor check

The report page can show today, but it lists only people who have captured something. This reader starts from the roster and the schedule, so it can say who is scheduled and silent.

What to notice
  • Magnus sets the flag scheduled_no_entries. The model doesn't work it out.
  • The answer says "as of 2:40 PM". The page keeps moving after that.
  • Schedules are planned hours. Nothing in Magnus says whether Ines is at her desk, and the assistant says so.
Decisions this raises
  • Which flags are worth having, and their thresholds. A dupe share flag needs a number from you.

8Voiding a bad capture

Sofia captured the company's own page by mistake. Jordan finds the capture by handle, reads what the void will do, and approves it. A void can't be undone.

What to notice
  • The handle check gives an admin the submission ID. Jordan never types one.
  • The preview says what the void does not do. Lifetime counters and deal credit stay as they are.
  • The last beat reuses the token with a different reason. Magnus refuses. Today's confirm.ts would have replayed the first result.
Decisions this raises
  • Whether lead gens should be able to flag a capture for review. That needs a table and an admin queue, so it is in the "later" group.

Under the hoodWhere report numbers come from

The Operations page takes one of three routes depending on the range. The report tool has to take the same one, or its numbers drift from the page. Pick a range to see the route and what the result says about itself.






  
One deadline
The report tool is an action. It registers the report, waits up to 25 seconds, reads today's live part and merges. If the warehouse hasn't answered, it returns state: "pending" and no numbers. Missing is never zero.

  
The page's definitions travel with the result
"Unique" means prospect-days, not distinct people in the range. Conversions ignore the source filter. A split top-posts list is merged from two top-ten lists, so it carries rankingPartial.

  
A size budget
Twenty-five rows by default and fifty at most, nested rows included. 64 KiB a result. No avatars or preview images. Text is trimmed to 500 characters with a flag. Sections default to the overview and specialists.

A retry never saves twice
The assistant sends a requestKey with each list. Magnus builds each line's key from the user, the request key, the source, the handle and the origin. The same line under the same key returns the saved capture. A deliberate second capture uses a new key and counts as it does on the web.

  
State is checked again at commit
A line already saved under the same key, or an item the same person already marked the same way, is reported as such with its void state. Any other change since the preview fails the whole commit and the assistant previews again. That covers a person who became do-not-contact, left the pool, or a batch that expired. It never skips a line silently.

  
The agent never creates a worker
On the web, an admin who captures gets a lead gen worker profile created or reactivated without being asked. In release 1 the day tools are for lead gens only. Each one checks the role in its own guard as well as in the catalog. For a lead gen, Magnus refuses a missing or inactive profile before it creates anything.

EngineeringWhat has to be built


Release 1 adds no table, no index and no field. Most of the work is pulling a "core" out of each existing function so the web and the tool run the same code, the way the closer tools already do.


Three fixes to code that ships today



  
A used token replays before the check
redeemConfirmation returns a used token's stored result at convex/mcp/confirm.ts:86. The argument check is at line 92, and the tenant is never compared. A used token sent with different arguments gets the first operation's success back. The fix checks user, tool, tenant and arguments first. Its messages also say "the closer".

  
The respark card shows a payment touch
The person panel filters payment events out at convex/respark/queries.ts:226. The batch card does not. lib/respark/people.ts:128 passes "payment recorded" through as a touch, and a test expects it. The MCP card drops it. Whether the web card should is your call.

  
My Activity lists voided captures
listMyRecentSubmissions doesn't filter voidedAt, while the figures above it exclude voided captures. The list and the totals can disagree. The tool returns a voided flag on each row. The web list should get the same.

The critique column is the mean of the five critics' scores for that seat's draft. Each round used fresh reviewers in the same seat. Both blocks in vote 1 were the same gap. The report tool promised team and specialist filters, and the snapshot route can't honour them. It would have returned workspace-wide numbers under a filtered question. Release 1's report tool now takes the page's own filter, source, and refuses any other. The one block in vote 2 was a Convex rule. The capture-rows tool planned to page an existing reader twice inside one query, and a query may make only one native paginated read. That tool is now an action that runs several guarded queries under one budget.
Vote 3 reached consensus. All five seats approved at 8/10 and nobody blocked. The disagreements below stay on the record.

Proposal and prototype. Nothing here is built. Every window below is simulated in this page, and nothing talks to Magnus, Claude, ChatGPT, Slack or Fathom. Every person, amount and workspace is invented. Client screens are approximations drawn to show the flow. File and line references point at the code as it was on 9 November 2026.

The admin assistant

Closers can already run their day in Magnus from Claude, ChatGPT or a terminal. This is the design for the same thing for owners and admins: 19 tools that answer questions about the floor, work the review queues, and keep the workspace healthy. Eight scenes below play each one out, with the admin's AI client on one side and Magnus on the other.

Short version

  • The piping is there, and it takes one coordinated change to open it to admins. The endpoint, sign-in, guard, confirm tokens, rate limit and audit all carry over. Two lists refuse admins today and have to change together, and the tool list and instructions are hard-wired to closers.
  • 19 tools, in three kinds. Ten read. Eight prepare a change and change nothing. One commits. A model picks among them by what the admin is doing: check the floor, ask a number, work a queue, decide an item, fix something broken.
  • An admin's agent sees every closer's deals and every payment, so writes work differently from the closer tools. A change to one record is prepared, read back, and committed with a token that pins the record's state. Payment reviews and covering a sick closer are never committed from chat. The admin approves them on a Magnus page, because a token proves two calls happened, not that a person agreed.
  • Off by default, and only the owner turns it on. Reading and changing are separate switches, and each kind of change has its own. Today a tenant admin could switch on AI access for their own role. That is one of six things to fix first.
  • It ships as one pull request, switched off. Twenty-one commits and one deploy, the way the closer assistant shipped. Nothing changes for anyone until the owner turns on reading, and nothing can be changed until the owner turns on a kind of change.

The ideaThree kinds of tool

The closer tools mix reading and writing freely, because a closer's agent only touches the closer's own deals. An admin's agent can reach everyone's. So every admin tool is one of three kinds, and the kind decides what it is allowed to do.

10

Read

Return numbers, queues, records and health. They change nothing and run without asking. Lists leave out emails, phone numbers, receipts and transcripts.

8

Prepare

Draft one change and return a preview. Magnus stores the draft and a fingerprint of the records it depends on. No deal, meeting or payment has changed.

1

Commit

magnus_commit applies a prepared change to one record. It takes the token and a short echo of the change, which Magnus checks against the preview. Money, losses and plans are approved in Magnus instead.

The catalogThe 19 tools

Eighteen are new and one, magnus_get_recording, is a closer tool opened to admins. Click a tool for what it does, what an admin would say to reach it, the code it is built on, and a sample call. The closer set is 16 tools, so an admin's client lists 19 and a closer's lists 16. Nobody sees both.

Two things every item carries make the set work as one. Each record in a result has allowedActions, worked out from its current state and what the owner has switched on, so the model is only ever pointed at a tool it can see. And each has openInMagnus, the link to its page, for everything that is better done there.

Act 1Switching it on

1The owner switches admins on

The AI assistants card has an "Admins" row that says "No tools yet". With a toolset behind it, the row becomes two: one switch for reading, and a set of switches for each kind of change.

What to notice
  • Reading and changing are separate. A workspace can run a read-only assistant for months.
  • Each kind of change is its own switch, so the owner can allow payment corrections and still keep results off.
  • An admin sees the card and can't change it. Today's backend would let them.
Decisions this raises
  • Whether a tenant admin should ever get changes, or only the owner. Question 1.
  • Whether the card should list who has connected and when they last used it.

Act 2Reporting

2The floor, and who didn't end their day

Three questions, three reads. The last one has no page in Magnus today. Closers' end-of-day reports are saved in a table and posted to Slack, and that is the only place an admin sees them.

What to notice
  • The floor table and the Overview page agree, because both read the same code.
  • The queue result names people and carries IDs and links. No email or phone number is in it.
  • "No report saved" is reported as that. The tool never says someone didn't work.
Decisions this raises
  • Whether the end-of-day reader should also get a page in the web app. Question 5.
  • Whether magnus_brief should include the names behind each count, or stay counts only as drawn here.

3Why is cash down?

The report pages show one range at a time. A "why" question means opening two ranges and three pages and doing the subtraction yourself. Here Magnus does the subtraction.

What to notice
  • Every difference in the answer was computed by Magnus. The model was told never to add or compare numbers itself.
  • Rates come with their numerator and denominator, and change in percentage points.
  • The agent says where the gap is and declines to say why. A number can't tell it that.
  • History is a few hours old, and the answer says so.
Decisions this raises
  • Whether a six-hour lag on history is acceptable when labelled. Question 6.
  • "Cash" means two things in the code today. See Where a number comes from.

Act 3Actions

4Billing, six at a time

Marking a payment reviewed means someone looked at the receipt. The agent can't see receipts, so it never reviews anything. It prepares a plan, and Jordan approves it on a page that shows the receipts.

What to notice
  • The agent names six payment IDs. It doesn't ask Magnus for "the clean ones", so there is no hidden rule choosing payments.
  • Magnus leaves out anything that can't be reviewed this way and says why: disputed, no receipt, a receipt that matches another payment, or one the admin logged themselves.
  • If one of the six had changed before Jordan approved, none would have been applied.
  • The agent reads the outcome from Magnus and doesn't take "Approved" on trust.
Decisions this raises
  • Whether even a single payment review should go through the page. Question 2.
  • Whether an owner may approve a plan an admin's assistant prepared. Question 3.

5Kim is out sick

Today this is the Mark unavailable dialog and then a three-step wizard. The reassignment moves the whole deal, so a follow-up next week moves with today's call. The plan shows that before anyone approves.

What to notice
  • The plan gives each deal one new owner. Jon's Monday follow-up moves with his deal, and the preview says so.
  • Approval applies the plan as stored. Magnus doesn't choose closers again at that moment.
  • The page says what Magnus doesn't do: the Calendly invite and host stay as they are.
  • The call nobody could take stays with Kim. Cancelling it would close a deal, so that choice is on the web.
Decisions this raises
  • The redistribute wizard stays exactly as it is in this pull request. It can hand two calls on one deal to different closers, and the tool's planner must not. So the planner is tested on its own rule, and compared with the wizard only where each deal has one meeting in everything that moves.
  • Whether Magnus should tell Alex and Sam, in Slack, that calls have moved to them. Nothing does today.

6A second opinion, decided

A change to one record: prepared, read back, committed. The commit is its own tool, so the client's permission prompt appears on the step that writes.

What to notice
  • Preparing changed nothing. The state panel shows one draft row until the commit.
  • magnus_commit repeats the change in words, and Magnus checks them against the stored preview. Claude's prompt shows "Grace Liu · reopen at Follow-up", not a token, and a commit that doesn't match is refused.
  • The call-back time comes back resolved in Kim's zone, so a wrong guess would show.
  • Kim's timeline will say "Jordan Park via Claude". The admin is the actor, never a pretend closer.
Decisions this raises
  • During a workspace's 14-day shadow run only the owner sees second opinions. The tool follows the same rule.
  • Second-opinion decisions leave no domain event today. This adds one for the web path too.

Act 4Maintenance

7Friday upkeep from a terminal

The same tools from Claude Code. Health is a read. Repairs are prepared and committed like any change. A setting that shapes future bookings stays on its page, and the agent says so.

What to notice
  • Health has four states. "Unknown" is honest about WorkOS and cron runs, where Magnus keeps no signal.
  • The agent splits the work: what it can prepare, and what is a person's decision on a settings page.
  • A retry reports "queued" with a receipt. The agent reads the queue again before it says fixed.
Decisions this raises
  • Calendly resync, webhook repair and the 30-day Fathom import stay on the web for now. They run as several steps that can't roll back together.
  • "Did last night's sync run?" can't be answered yet. Crons keep no run record.

Act 5When things go wrong

8Five ways it holds

Pick a case. Each one is a rule the tools enforce themselves, so nothing depends on the model behaving.

What to notice
  • A stale preview writes nothing and names who changed what.
  • Text from a lead, a closer or another agent comes back tagged with its author. Text one agent writes is tagged for the next agent to read.
  • A kind of change that is switched off isn't in the tool list at all.
  • The assistant path refuses a result on a call that hasn't started. The web path allows it today.
  • A cold report returns pending with no numbers. It never returns a zero.
Decisions this raises
  • The web path's missing time check is listed under things to fix first, for the assistant path only. Whether to add it to the web too is yours.

The web keeps its laneMagnus has two interactive report workers. Assistants may hold one running job and two queued across the whole deployment, counted per job, since one comparison can create several. SafetyWhat stops an agent doing damage

Two investigators, one from each model family, worked the same question separately: what should an agent acting as an admin be allowed to do? They agreed on the answer below. The sharpest point was about the confirm token the closer tools use. It stops the model changing an amount between the read-back and the write. It doesn't prove a person said yes, because an agent can make both calls itself.

ContractWhat the model sees

Instructions sent when an admin connects. The tools enforce every rule themselves. These lines save wasted calls.

You're connected to Magnus as Jordan Park, an admin at
Northwind Coaching. Times are in America/Tegucigalpa unless
a result says otherwise.

1. Start with magnus_brief. It holds today's floor, every
   queue's count and anything red in health.
2. Take every number from Magnus, with its definition and
   as-of time. Never add, average, compare or estimate one
   yourself. Ask magnus_numbers to compare.
3. Take every ID from a tool result. Never guess one from a
   name. Use magnus_lookup.

   read the preview to the admin word for word, and only

   magnus_commit, unchanged.

How the tools are marked for the client. Read tools carry readOnlyHint. Prepare tools are marked as writes that aren't destructive, because they store a draft. magnus_commit is the only tool with destructiveHint, so the client's serious prompt is at the commit. Its arguments repeat the change in words, which Magnus verifies, so the prompt reads as a sentence. The closer tools put preview and commit on one tool, so the client's prompt can't tell the harmless call from the one that writes.

LimitsWhat stays in the web app

These never become tools. A result that touches one carries a link to its page.

  • Merging peopleThere is no unmerge. It needs the two records side by side.
  • Booking-review decisions"Keep separate" also closes sibling reviews the preview wouldn't show.
  • Cancelling a call during an absenceIt closes the deal as lost.
  • Event types, coverage, programsThey decide how every future booking and payment counts.
  • Business day, Slack channels, portal linksOne triggers a rebuild, one can post to a channel, one logs people out.
  • Calendly resync, webhook repair, Fathom importSeveral steps that can't roll back together. Later, with receipts.
  • Connecting or disconnecting an integrationBrowser redirects and secrets. A key must never pass through a model.
  • Invites, removals, role changesThey change who can sign in, across WorkOS and Magnus.
  • AI access and second-opinion switchesAn agent must never widen its own access.
  • Exports and receiptsBulk personal data and proof images stay out of a model provider.
  • Everything under /adminThat is Magnus's own cross-workspace control panel. No workspace admin reaches it.

DeliveryOne pull request

This ships as one pull request, with no phases. The closer assistant shipped the same way: one pull request of 200 files and about 28,000 added lines, built and reviewed commit by commit. Expect this one to be the same order of size. Each commit is meant to pass lint, typecheck and the tests by itself, and no commit before the eleventh changes what an admin's sign-in can do.

The merge gate. Everything here passes before the pull request merges.

AreaWhat has to pass
AccessAdmins are refused until the owner switches them on. A tenant admin can't switch on admin access or unblock themselves. A kind of change can't go on while reading is off. A tool that is switched off is missing from the list. A closer can't see or call an admin tool. Another workspace's ID gives "not found", tested with two made-up workspaces.
ReadsThe same number from the page's own path and the tool, for today, a past day, a split range and a cold cache, with each page's warehouse switch on and off, for all nine reports. No list returns contact details, receipts or notes. A planted instruction comes back only inside an untrusted field. A truncated input gives no difference. A failed report job frees its place, a retry isn't counted twice, and a spent allowance is answered without queueing. After the assistant has spent its allowance a page is still served, and no assistant run writes to the pages' cache.
Changes to one recordFor each tool: prepare, change the record as someone else, and the commit writes nothing. Commit twice gives one event. A commit whose words don't match the preview is refused. The old web code and the new core leave identical rows. A sibling payment that alters a correction's effect on enrollments refuses it.
PlansOne stale row in 20 means none applied. A coverage plan gives each deal one owner who is free for every meeting that moves. A meeting added, removed, moved or resized after the preview refuses the plan. Of two admins approving competing plans for one closer, the second is refused. A closer's token opened on the approval page gives "not found". Preparing a loss returns only a link. Another admin's approval is refused, and so is an expired plan. A second click on Approve returns the first result and applies nothing.
SwitchesOff between prepare and commit refuses. Off then on doesn't revive a token or a plan, and that includes the reading switch. Neither does block then unblock.
CompletenessEvery operation any tool offers can be carried through to its end in a test.
Closer toolsThe existing closer tests pass unchanged apart from the confirm fix and the untrusted marks, each of which adds a test.

Rolling back. The first resort is the switches. Turning reading or a kind of change off takes effect on the next call and stops every open token and plan, approval on the web page included.

A code rollback is not a plain revert. Once a workspace has values in the new fields, the old schema would reject those records and the deploy would fail, and the old clean-up would delete receipts an hour after they expire. So the rollback is a prepared change that keeps the schema and the receipt-keeping clean-up, keeps the fixes, removes the admin roles and tools, and takes the approval page down. The closer assistant's plan did the same. It is rehearsed on a dev deployment with real-looking data before merge. The four commits that split code the web app runs today, 7 to 10, carry no schema and can each be reverted alone if a web page regresses.

DecisionsQuestions for you

  1. Should a tenant admin ever get changes, or only the owner? The switches allow either.
    Yes, per kind of change, and only when the owner switches it on. Jordan works Billing every day and is the person who would use it most.
  2. Should every payment review go through the approval page, even one payment? A chat token would be quicker for a single payment.
    Yes. Reviewing means seeing the receipt, and the assistant can't show it. One rule is also easier to explain than two.
  3. Who may approve a plan?
    The admin whose assistant prepared it, or the owner. Whoever approves is recorded as the actor.
  4. How long should receipts be kept? Closer confirmations are pruned an hour after they expire.
    One year for a used admin confirmation. Unused ones go as they do now.
  5. Should end-of-day reports get a page in the web app as well? With this design the assistant would be the only place outside Slack to see who ended their day.
    The tool in this pull request. A small page under Team afterwards, built on the same reader.
  6. Is a six-hour lag on history acceptable when every answer is labelled with its as-of time?
    Yes. Today and any single day are live. A correction made this morning to last week's payment shows on the record at once and in the weekly total after the next sync.
  7. Should the role-change bug be fixed now? It is listed as fix 3 and is unrelated to assistants.
    Yes. It is commit 4, a one-line server check, and it matters more once a role decides what an assistant can reach.
  8. Should preparing a change ask for permission too? Preparing stores a draft and changes no record. Marked honestly as a write, it makes ChatGPT prompt twice: once to prepare, once to commit. Marked read-only, it prompts once.
    Keep the honest marking, and measure the cost in the client check before merge. If two prompts make people click through without reading, switch it.
  9. What about an agent that drives a browser? The approval page assumes a person is at the keyboard. An agent with control of the admin's browser, such as Claude in Chrome, could press Approve.
    Record how each approval arrived, and say on the page that approving is yours to do. If browser agents become common among your admins, ask for a fresh sign-in before a money plan applies.
  10. Should Magnus tell a closer when calls move to them? Nothing does today, from the wizard or from a plan.
    A Slack message to the closer when a plan is applied, in a later change. It isn't needed for the tools to be safe.

The order on the day

Nine steps from merge to switched on. Amber steps are checks that can stop the run; red steps write data. Every step says what makes us stop.

  1. 1

    Read-only checks on production

    The five queries in D12, run right after a sync. They size the backfill and show whether D2 to D4 matter in your data.

    Stop ifThe backfill count is far from what the code predicts. Then something writes call types in a way I haven't found.
  2. 2

    Block the two new tables in Fivetran

    Export jobs and the backfill ledger. New Convex tables sync to ClickHouse unless the connector blocks them, as the ClickHouse plan notes.

    Stop ifThe connector still lists either table as allowed.
  3. 3

    Apply 0004_views.sql

    pnpm ch:migrate, right after a sync. Views are CREATE OR REPLACE, so the file can run twice, and nothing reads the new ones yet.

    Stop ifA view fails to create. Nothing depends on it until step 8.
  4. 4

    Merge and deploy

    Convex and the app deploy together. New bookings get call types by the new rule. Users still see the old pages.

    Stop ifAnything on the old pages moves other than the first and follow-up split of calls booked after the deploy.
  5. 5

    Dry run the backfill

    An internal query computes the new type for every meeting and returns what would change, by month and by closer, with sample IDs. It writes nothing.

    Stop ifThe count differs from check 1 by more than the bookings made since it ran.
  6. 6

    Run the backfill, then its assert

    Small batches through patchMeetingLifecycle, so the meeting aggregate, the Operations projection and the deal's meeting refs follow. Each change is written to the ledger first. The assert then reads every meeting again.

    Stop ifThe assert fails or the per-closer totals moved. The reverse mutation reads the ledger and restores every old type exactly.
  7. 7

    Sync ClickHouse

    Start a Fivetran sync. ClickHouse picks up the patched meetings, and every cached answer recomputes on the new watermark.

    Stop ifThe sync doesn't land within the hour. Wait; nothing new is on yet.
  8. 8

    Parity, page by page

    pnpm analytics:parity for each new page over yesterday, last month and last 90 days, then each page with ?analytics=preview.

    Stop ifAny difference. That page stays dark; the others can still go on.
  9. 9

    Switch each page on

    analytics/switch:enable per page. Its old route redirects from then on (D11).

    Stop ifA number looks wrong afterwards. switch:disable brings the old page back without a deploy.

The one thing outside the PR is deleting the old pages, their readers and the aggregates only they read, two weeks after the switch. That's the repo's own rule in docs/plans/clickhouse-reporting.md §12.1, and it's deletion only. D11 asks whether you want it in the same PR instead.

Ten rules the backfill follows

01 · Dry run first

Nothing writes until you've seen the numbers

An internal query applies the rule to every meeting and returns the changes by month and closer, with sample IDs. Its count should match check 1 in D12.

02 · One rule

The writer and the backfill call the same function

The booking writer, the backfill and, with D5 = C, the result recorder all call one function. The backfill can't give a past meeting a type a new booking wouldn't get.

03 · Side effects

Every change goes through patchMeetingLifecycle

It re-keys the meetingsByStatus aggregate and queues the Operations meeting projection. A raw ctx.db.patch would leave Team Performance counting the old type, with no error.

04 · Idempotent

Only meetings that differ get written

Each batch compares the stored type with the rule before it writes. A second run changes nothing and logs zero.

05 · Resumable

Small batches with a cursor

Each change also rebuilds the deal's meeting refs and search rows, so batches stay small: 25 changes to start, sized from the dry run. Each batch schedules the next and logs meetings read and changed. A failed batch stops the chain, and the cursor resumes it.

06 · Paired assert

An assert* migration checks the result

It reads every meeting again and fails on the first one whose stored type differs from the rule, as docs/agents/convex.md asks of every migration.

07 · A way back

A ledger makes the reverse exact

The old types can't be recomputed: meetings from before v0.6 were typed by call time, later ones by insert order. So each change writes the meeting ID, old type and new type to a ledger table before the patch. The reverse mutation reads it back, and a test runs forward, then back, and compares.

08 · Writer first

The new writer deploys before the backfill runs

No booking made between the deploy and the backfill keeps the old type, and the dry run sees the same rule production uses.

09 · Totals stay put

Calls per closer, day and status don't move

Only the first and follow-up split changes. Sales Calls and Team Performance are read before and after for October; their totals must match exactly.

10 · Edge cases in tests

The chains that break naive rules

Two moves in a row. A move, then a no-show rebook. A replaced slot on another deal after a merge. A meeting with no type. A follow-up booked before the first call's result is recorded.

What the backfill never touches: payments, credit rows in dealAttributions, deal stages, and the buckets of the Operations projection. Its only side effects are the ones patchMeetingLifecycle already makes for a type change.

D1 Ranges No data change

When a range includes today, where does today come from?

Today and a single day read Convex. Longer ranges read ClickHouse. The open question is the range that ends today, such as This week on a Thursday.

What the code does today

The planner already splits these: ClickHouse through yesterday, Convex for today, merged on the page. Fivetran syncs every six hours. After the business day changes at 1:00 AM, the history answer is recomputed, but from the last sync, which can be from before midnight. The freshness line then reads "Today live · earlier days as of 10:05 PM", and anything logged late yesterday is missing until the next sync.

Who gets the credit

D2 Credit for calls New No data change

When a deal changes closer, who keeps its past calls?

This isn't in the first report. I found it while building the cases for D3, and it changes show rates and close rates more than anything else here.

What the code does today

Three things change a deal's closer: a follow-up booked on another closer's Calendly, a reschedule to another host, and a redistribution for a closer's unavailability. Each one calls syncOpportunityMeetingsAssignedCloser, which sets assignedCloserId on every meeting of the deal to the new closer, past ones included. Reports count calls, no-shows and the close-rate cohort by that field, so the earlier closer's held calls and no-shows move to the new one, whenever it happens.

Access follows the same field, so the writer has to keep doing this. The credit rows don't move: each meeting keeps its booking_closer row naming the host it was booked with, and a redistributed meeting gets a reassignment row.

What a word means

D5 Call types Partly new Sets the backfill

What makes a call a follow-up?

The first report said a moved first call should stay a first call. Working through the cases turned up a second question: what about a call rebooked after a no-show?

What the code does today

A new meeting is a follow-up when its deal already has any meeting. A Calendly reschedule cancels the old slot and inserts a new meeting, which therefore becomes a follow-up. A rebook through the no-show link also points back with rescheduledFromMeetingId, at a meeting that stays a no-show.

The same field decides DM goals: Booked Calls, its export, the Overview leaderboard and a ClickHouse template count a DM team's bookings as "anything but a follow-up". A moved call is a first call, but it isn't a new booking, so changing the type means those four also have to skip replacements.

D12 Before the backfill Reads only

May I run five read-only queries on production first?

Every number in the cases above is invented. Five queries would show which of these decisions matter in your data, and how big the backfill is.

How they'd run

ClickHouse holds production data only, so these run there, through the read-only login, in the minutes after a sync. I'd also read the last few sync times from analyticsSync to settle D1. The results come back to you in chat and never go in the repo, which is public.

Check 1 · D5, D6, the backfill

Replaced calls, their types, and DM credit on them

SELECT
  toStartOfMonth(fromUnixTimestamp64Milli(s.scheduled_at_ms, 'America/Tegucigalpa')) AS month,
  countIf(p.status = 'canceled') AS replaced_moves,
  countIf(p.status = 'no_show') AS rebooks_after_no_show,
  countIf(p.status = 'canceled' AND s.call_classification = 'follow_up') AS moves_filed_as_follow_up,
  countIf(s.id IN (SELECT meeting_id FROM analytics.attributions
                   WHERE tenant_id = {tenant_id:String} AND role IN ('dm_team', 'dm_closer'))) AS replacements_with_dm_credit
FROM analytics.meetings AS s
INNER JOIN analytics.meetings AS p ON p.id = s.rescheduled_from_meeting_id
WHERE s.tenant_id = {tenant_id:String}
GROUP BY month ORDER BY month
Check 2 · D2

Held calls and no-shows now on a different closer

SELECT
  count() AS held_or_no_show,
  countIf(c.meeting_id IS NULL) AS no_closer_row,
  countIf(c.meeting_id IS NOT NULL AND c.closer_id != m.assigned_closer_id) AS now_on_another_closer
FROM analytics.meetings AS m
LEFT JOIN (
  SELECT meeting_id, JSONExtractString(argMax(source_json, attributed_at_ms), 'userId') AS closer_id
  FROM analytics.attributions
  WHERE tenant_id = {tenant_id:String} AND role = 'closer' AND meeting_id IS NOT NULL
  GROUP BY meeting_id
) AS c ON c.meeting_id = m.id
WHERE m.tenant_id = {tenant_id:String} AND m.status IN ('held', 'no_show')

Cash whose payment names someone other than the first call's closer

WITH first_held AS (
  SELECT opportunity_id, argMin(id, scheduled_at_ms) AS meeting_id
  FROM analytics.meetings
  WHERE tenant_id = {tenant_id:String} AND status = 'held'
  GROUP BY opportunity_id
), first_closer AS (
  SELECT f.opportunity_id AS opportunity_id,
         JSONExtractString(argMax(a.source_json, a.attributed_at_ms), 'userId') AS closer_id
  FROM first_held AS f
  INNER JOIN analytics.attributions AS a ON a.meeting_id = f.meeting_id
  WHERE a.tenant_id = {tenant_id:String} AND a.role = 'closer'

01 / System model

The system has two kinds of truth

A meeting, opportunity, lead or payment is an authoritative business record. Operations totals are a derived view of those records. This change keeps the business write and the obligation to update that view in the same mutation, then lets a reporting worker compute the current answer.

Accept the event

Store its payload, delivery receipt, provider facts and queued job together. Return HTTP 200 after acceptance, before the booking worker finishes.

Apply a safe booking

The worker checks the host, identity and booking relationship. It commits CRM writes with the receipt outcome, or leaves a reviewable blocked/failed receipt.

Project current records

The report worker compares the meeting's current contribution with the contribution it previously recorded. It updates the difference atomically.

What Workpool owns

The two pools schedule bounded internal mutations and limit how many run concurrently. The application's receipt, projection and sweep rows hold business progress, reasons and retry generations. There is no Workflow component in this refactor: the implemented units are database transactions and paged jobs, rather than a journaled sequence of external calls. Booking work and reporting work have separate pool budgets, so a report rebuild does not occupy the booking pool.

What users see

A closer's successful command returns after the business transaction commits. Operations totals catch up afterward; pending or failed reporting work appears in the health banner. Admin diagnostics expose delivery outcomes and reviewed retries. Question answers display their original labels, even though storage keys are now hashes.

The old operations stats table remains for migration/verification context. Production operations readers move to operationsMeetingStatsV2. Existing synchronous aggregate components still participate in source mutations.

02 / Acceptance boundary

HTTP acceptance is separate from booking success

The existing HTTP endpoint still checks the tenant's signing secret and webhook signature. Its persistRawEvent call creates the durable acceptance record. The asynchronous booking result appears later in the delivery receipt.

The deduplication key

For invitee.created and invitee.canceled, the SHA-256 key includes event type and invitee URI, scoped by tenant. Repeated delivery cannot create a second receipt for that logical event.

For mutable events, the key also includes provider created_at, or the raw payload if it is missing. No-show fact ordering uses the parsed provider time; missing or invalid time falls back to receivedAt.

What survives retention

Resolved raw payloads can expire after 30 days. Compact receipts and provider facts stay, so the identity of an accepted event does not disappear with its original JSON.

Blocked and failed events retain their payload for recovery. Legacy adoption consolidates duplicate raw rows around a canonical receipt and retains its payload when unresolved.

Atomic acceptance means one committed unit. If the acceptance mutation throws, its new payload, receipt, fact and job are not committed. If the HTTP response is lost after commit, the provider's retry finds the receipt.

Atomic mutation behavior is a Convex platform guarantee. The deduplication lookup and queue call are the application's implementation of that guarantee. See Convex mutation transactions and Convex OCC and atomicity.

03 / Booking decisions

Unsafe bookings become visible decisions

The booking processor is now an internal mutation. A recognized business block comes from the nested booking mutation; the processor catches it and stores a fixed reason on the receipt. An unexpected exception rolls back the worker mutation, then the separate Workpool completion callback records failure.

Receipt stateWhat it meansBusiness effect and next action
queuedThe application has recorded work to run.It is not a separate running state. Wait for the worker; a stale queue requires investigation.
appliedA tracked booking was matched and the relevant event was reconciled.A harmless late event can apply without changing a completed outcome. Applied does not imply “new meeting inserted.”
ignoredUnsupported event type or a known non-closer host.No tracked sales booking is created for that ignored event. Normal retry accepts only blocked or failed receipts.
blockedMissing host/booking, conflicting identity, invalid link, ambiguous relationship or unsafe historical event.Retain payload and reason. Resolve the cause and use a reviewed retry. Some blocks still require a scoped data repair.
failedUnexpected processing exception or canceled work.Worker changes roll back; a later callback records a fixed reason. Investigate and retry the current failed generation.

Checks that change the outcome

  • Host must map to an active same-tenant closer. Unknown/inactive hosts block; known non-closer hosts ignore.
  • Email, accepted phone and social identifiers must resolve consistently. Merge chains must stay within the tenant.
  • Placeholder/repeated-digit phone values are excluded from matching. A real phone conflict cannot silently attach another email.
  • Internal booking links must point to valid same-tenant opportunity, follow-up and source-meeting relationships.
  • Provider reschedules use explicit old_invitee where available. Ambiguous fallback candidates block.
  • An event older than a newer opportunity update blocks for review. Derived meeting references no longer advance business updatedAt.

Question labels now stay in values, while record keys use q_ plus a SHA-256 digest of label and repeated-label occurrence. This accepts Unicode and multiline labels without making them Convex object keys. Display components read the preserved labels; legacy answers can be upgraded without duplicating the response.

04 / Reporting correctness

A saved outcome and an updated report have different commit times

Closer and admin commands still enforce access and valid transitions. The lifecycle helper takes IDs, reads the current meeting and opportunity, writes the source change, updates the existing synchronous aggregates and requests a V2 projection. A failure in those synchronous steps still aborts the business command.

A later V2 worker failure cannot roll back the already committed closer command. It can leave the report stale. The health banner shows pending reporting work and failed jobs; the diagnostics tab lets an authorized operator retry failed work after fixing its cause.

The accounting rule

Each meetingProjections row records what that meeting contributed last. The bucket key includes UTC day, assigned closer, booking program, sold program, attribution team, DM closer, current opportunity status and meeting status.

bucket count = number of recorded meeting contributions with that bucket key
changed meeting = remove its recorded old contribution + add its current contribution

A repeated job that sees the same contribution changes no counts. A changed contribution decrements the old bucket and increments the new one. These writes and the saved contribution commit together. A missing old bucket throws instead of silently accepting broken accounting.

When a meeting is deleted through a path that requests projection work, the worker removes its recorded contribution. Retry alone cannot repair a source deletion that bypasses the hook; migration assertions and reviewed reconciliation must catch it.

05 / Event order and failure

Walk through the cases that caused the risk

Select a scenario to follow the implemented decisions. These are explanations of the code and linked tests, not live executions against a deployment.

Provider facts have a narrower authority than closer outcomes

Cancellation is permanent for a particular invitee URI. No-show create/delete uses the latest provider timestamp, with deletion winning ties. Reconciliation changes scheduled meetings and provider-marked no-shows. It preserves completed meetings and manually marked no-shows.

An old booking event can update its own meeting only when the state is eligible. It can update the opportunity only when that event is its current booking, or its latest meeting when no current event URI exists, and the opportunity state is one of scheduled, no_show or canceled.

06 / Bounded work

Large histories advance through durable pages

An opportunity-wide change requests a sweep job. Each page reads at most 64 meetings and requests projections by ID. Its next cursor and next job generation are saved together. A new request during an active sweep sets dirty; after its final page the job restarts from the beginning if needed.

08 / Activation sequence

The new totals must be rebuilt from authoritative records

The widened schema retains legacy stats and adds receipts, provider facts, projection records, sweep jobs and V2 buckets. The rebuild reads meetings and current opportunities. It does not seed new counters from the totals already known to be inflated.

10 / Decision boundary

What I would require before production activation

The refactor addresses the observed accounting, ordering and recovery mechanisms. The local evidence supports moving to joint validation. It does not justify treating production repairs or throughput as already settled.

Supported by code and tests

  • One recorded meeting contribution prevents the tested duplicate-count outcomes.
  • Early cancellation and reversed no-show delivery reconcile to the tested final state.
  • Paid/completed outcomes survive the tested late cancellation.
  • Ambiguous identities, bad links and unsafe history stop with retained outcomes.
  • Reporting failure can be observed and retried after its cause is fixed.

Still requires joint validation

  • Signed real webhook acceptance, response loss, concurrent duplicates and provider retry behavior.
  • Concurrent source writes versus projection workers, dirty sweep restart and callback failure.
  • Full migration, freshly rerun assertions, activation and rollback on realistic staging data.
  • Exact report reconciliation across all affected readers, including overflow/fallback paths.
  • Admin UI access and recovery workflow in a browser; measured queue age, throughput, drain time and OCC contention.

The design still has these limits. Reports can lag committed business writes, and permanent mutation failures require reviewed recovery. The current migration activation gate also relies on correctly ordered operational verification rather than a generation-bound proof. Those are real limits to assess before approving deployment.
